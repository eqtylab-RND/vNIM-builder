cuAttest · how it works

The key inside the GPU

You can hash a model file on disk. That says nothing about bytes in GPU memory ten minutes later. cuAttest hashes the specific VRAM spans a client submits and signs that result with private state retained in device memory, away from the workload.

The idea

Two processes, one secret each

The notary owns a P-256 private key that was generated inside a CUDA kernel and lives in device globals. It never loads a model. The workload owns the weights and never sees the key. They meet only over CUDA IPC handles, which let the notary read the workload's live memory without copying a byte of it.

The split keeps the signing state away from the workload. It does not bind submitted spans to an executing graph: a compromised workload can ask the service to attest decoy buffers. A stronger inference claim needs a trusted component that selects the runtime's actual tensors independently of that workload.

The ceremony

What happens, in order

  1. Keep signing state away from the workload

    The trusted notary obtains a 32-byte operating-system CSPRNG seed. A kernel hashes it into a P-256 private scalar and retains that scalar in device globals. CUDA timing and scheduling effects are not credited as entropy. The host knows the seed and can reproduce the scalar; device storage isolates it from the untrusted workload, not from the trusted host. It dies with the process, so a notary's identity spans one run.

  2. Identify the module before loading it

    An independent host BLAKE3 implementation hashes the source and CUBIN before CUDA loads those bytes. A cache sidecar binds both digests, so architecture-named machine code is rejected when the source changes. Both content ids are signed.

  3. Take handles, not copies

    The workload hands over a CUDA IPC handle per allocator segment. The notary maps each unique segment once and finds a tensor at segment_base + seg_off + t_off. Producer ordinals may be remapped, so it checks the driver-reported allocation owner and complete span before launching a hash, then the producer releases its process-owned storage lease after the response.

  4. Hash in place, on the GPU

    BLAKE3 over the live bytes: a cooperative grid processes fixed 1 KiB chunks in 128 KiB scheduling tiles. Seven tree levels stay in block-local shared memory, then grid-wide barriers merge the much smaller set of tile CVs. The ordered tensor digests are folded into one model root in that same kernel launch.

  5. Measure and sign atomically

    The serialized request captures a server timestamp. The measurement kernel privately publishes its computed root to a small same-stream finalization kernel, which consumes it exactly once before another client can intervene. It writes the document — including the GPU ordinal and both code CIDs — and the statement manifest with the device-resident key.

Measurement

From bytes in VRAM to a content id

The digest is not merely a hash — it is the content id. CIDv1, raw codec, BLAKE3-256, so a tensor's digest is exactly what a content-addressed system would call that tensor.

The signature

What actually gets signed

One atomic call returns a measurement document with a detached P-256 signature, plus a versioned manifest of statements. The signed document commits to the root/count, server timestamp, GPU ordinal, signer DID, source CID and CUBIN CID. Verification also reconstructs and checks the credential JWS signature against the same pinned GPU key; omitting the manifest is rejected as a downgrade. The service adds its own IdentityAttestation before returning — signed by a different, durable key, and reported as unverified unless that key is pinned too.

Boundaries

What a signature here does and does not prove

It provesIt does not prove
The measurement kernel read these bytes from the submitted, bounds-checked spans in this GPU during the request. That the runtime computed correctly with them. A server can hold perfectly attested weights and still produce nonsense.
The measurement was produced by code whose content id is in the same document. That the supplied spans are semantically framework tensors or were used for inference. The client chooses the ranges; valid decoy buffers can be attested.
The signer retains its private scalar in device memory, away from the workload. Anything about the host. No TEE quote, no TPM, no platform attestation.
Reproducibility: the same weights measured again yield the same root. That the model file on disk matches — this measures resident memory, and a loader that transformed the weights gives a different root by design.

The notary is the trusted component

It holds the key, so it could in principle sign a root it did not measure. The split keeps that key away from the workload, but the workload still chooses which buffers to submit. Binding evidence to the tensors actually used by inference requires a trusted runtime integration or tensor enumerator outside cuAttest.

And because the key dies with the process, evidence binds to a run rather than to a long-lived identity. Restart the notary and the did:key changes — treat that as a feature to design around, not a wrinkle.

Using it

Three commands and six lines

cuattest build-kernel     # compile the CUBIN for this GPU (no GPU needed to build)
cuattest selftest         # keygen, hashing, signing — end to end
cuattest serve            # HTTP on 127.0.0.1:8077
from cuattest.client import Client
from cuattest.ipc import share_model

names, refs, keepalive = share_model(model)   # zero copy
receipt = Client().sign(refs, "my-model")      # atomic measure + sign
del keepalive                                  # only after request returns

Hold keepalive until the request returns. Freeing a tensor early lets the caching allocator hand its segment to something else while the notary is still reading it. The client then retires its process-owned storage lease so repeated model unloads reclaim VRAM. A timeout or disconnect instead quarantines the lease until server completion is independently known. Re-measurement requires a fresh one-shot refs list from share_model(). Its registry state survives dictionary copies, and an active Client claim cannot be released early.

The client connects directly and ignores environment proxy settings: a proxy response cannot prove that the same-host notary has closed its CUDA mapping.

A containerised client needs --ipc host as well as network access: the handles only resolve inside a shared IPC namespace. They are separate requirements for separate reasons, and getting only the first gives you a client that connects and then fails every measurement.
